# Безопасность общего холста (App Review 1.2), админка и автодеплой — проект

Статус 19.11.2026: проект согласован владельцем (решения — §8), реализация начинается с §6. Повод — отказ App Review по Guideline 1.2 (user-generated content) для iPad-приложения. Wire-формы здесь — предложение; нормативными станут после переноса в backend `docs/protocol.md` / `docs/admin-api.md`.

## 0. Принципы

- Новый посетитель видит только холст, как сейчас. Ни одного нового экрана, баннера или постоянной кнопки до того, как человек сам что-то сделает.
- Всё новое — внутри уже существующих мест: палитра, долгое нажатие, системные меню и sheet'ы. Тексты короткие, спокойные, без юридического тона на экране; юридический текст — по ссылке.
- Безопасность не ценой приватности: авторы остаются анонимными, секреты рисования не покидают устройство, жалобщик не раскрывается автору.

## 2. Согласие с условиями

- **Web:** страницы `/terms` (EN/RU, как `/about` и `/privacy`, в sitemap). Суть одним абзацем сверху: холст общий и публичный; запрещено сексуальное, насилие, ненависть, травля, незаконное, спам; такое удаляется, авторы блокируются; жалобы — в приложении или на `support@endlessdrawing.com`; ответ в течение 24 часов. Дальше — стандартные условия использования. Публичный холст сайта не меняется.
- **iOS:** смотреть холст можно без согласия. Первое касание Pencil (или пальцем, где он рисует) не начинает штрих, а открывает компактный sheet (medium detent):

```
┌──────────────────────────────────────┐
│  Before you draw                     │
│                                      │
│  Everything here is public and       │
│  stays visible to everyone.          │
│  No sexual, violent, hateful or      │
│  illegal drawings — they are         │
│  removed and their authors blocked.  │
│                                      │
│  Terms of Use ›                      │
│                                      │
│  [            I agree             ]  │
└──────────────────────────────────────┘
```

  Принятая версия (`terms.v1`) хранится в UserDefaults; новая редакция условий спросит ещё раз. Ничего не отправляется на сервер до согласия. В App Review notes описать, где sheet.

## 3. Жалоба, скрытие и блокировка (iOS)

Палитра получает одну новую кнопку — `…` (системный `Menu`) в заголовке рядом с ✕:

```
 Brush                        ⋯   ✕
                         ┌───────────────────┐
                         │ Report drawing…   │
                         │ Show hidden (12)  │  ← только если что-то скрыто
                         │ Terms of Use      │
                         │ Contact support   │
                         └───────────────────┘
```

**Report drawing…** закрывает палитру и включает режим выбора: сверху маленькая капсула, холст можно двигать как обычно, тап по штриху отмечает его (до 20, хит-тест как у ластика):

```
        ┌────────────────────────────────┐
        │  Tap drawings to report   3  ✓ ✕│
        └────────────────────────────────┘
```

✓ открывает системный `confirmationDialog` с причинами: Sexual · Violence · Hate or harassment · Illegal · Spam · Other — и переключатель **Hide everything from this author** (по умолчанию включён). После выбора:

1. Отмеченные штрихи сразу скрываются локально (и все штрихи автора при блоке) — это «немедленное удаление из ленты».
2. Уходит `stroke.report`; при отсутствии сети — повтор из очереди, как у create.
3. Короткий toast: «Thanks. Hidden for you — we review reports within 24 hours.»

**Show hidden (n)** — список «скрыто: n штрихов, m авторов» с кнопкой «Show all again». Без превью скрытого. Список скрытого и блоков хранится только на устройстве.

Свои штрихи пожаловать нельзя (`own: true` не выбирается); свои удаляются Undo/ластиком, как сейчас.

## 3a. Веб: та же палитра и те же жалобы (20.11.2026)

По решению владельца палитра сайта унифицирована с iPad, веб-инструменты сохранены:

- Шапка как на iPad: «ручка» (перетаскивание палитры мышью, пером или пальцем; на телефоне — bottom sheet без перетаскивания), заголовок «Кисть», `⋯`, ✕.
- Меню `⋯`: «Пожаловаться…», «Показать скрытое» (только если что-то скрыто), «Рисовать пальцем» (только на устройствах с touch), «Условия использования» (`/terms`, новая вкладка), «Написать в поддержку» (`mailto:support@endlessdrawing.com`).
- Цвета: те же шесть пресетов + круг «свой цвет» (системный выбор цвета браузера, где есть — с пипеткой) и строка недавних своих цветов (до 7, пресеты не повторяются; `localStorage`). Поле HEX, инструменты Рука/Ластик и кнопки масштаба остаются — это веб-дополнения для мыши и клавиатуры.
- Рисование пальцем: пальцы рисуют, пока не встретилось перо; потом только двигают холст (одно уведомление). Явный выбор в меню побеждает. Оба флага в `localStorage` (`endless-drawing.input.v1`).
- Жалоба: тот же путь, что на iPad — капсула снизу, тап выбирает чужой штрих (до 20, допуск 12 px, свои не выбираются), пунктирная рамка, диалог с причинами и «Скрыть всё от этого автора» (вкл.), после отправки — скрыто сразу и короткое сообщение. Веб говорит на v5 (`endless-drawing.msgpack.v5`, offered первым); на v4 жалоба не отправляется, но локальное скрытие остаётся. Код `banned` — короткое сообщение, штрих не остаётся «ожидающим».
- Хранение: скрытые id — `localStorage` (5000), блок авторов — `sessionStorage` (1000): author tag зависит от секрета вкладки, который тоже живёт в `sessionStorage`, поэтому блок автора действует, пока жив этот секрет. Жалоба при этом уже ушла модераторам.
- Согласие с условиями перед первым штрихом в вебе не показывается (принцип «никаких экранов до действия»; App Review касается приложения); условия — в меню и на `/terms`.

## 4. Протокол и backend

### MessagePack v5 (`endless-drawing.msgpack.v5`)

Новый subprotocol, чтобы строгие клиенты v2–v4 не встретили новых полей. Всё v4 без изменений, плюс:

- **`author`** в каждом объекте штриха: `base64url(HMAC-SHA256(author_key, viewer_owner_digest ‖ stroke_owner_digest))[0..16]`. Метка своя для каждого зрителя, как уже вычисляемый `own`: внутри одного зрителя позволяет скрыть всё от автора, между зрителями метки не сравниваются, `owner_digest` и секрет не раскрываются. `author_key` — отдельный серверный секрет, ротация = сброс блоков у всех (допустимо).
- **`stroke.report`** `{request_id, stroke_ids: [≤20 UUID], reason: sexual|violence|hate|illegal|spam|other, block_author: bool}` → `ack {operation: "stroke.report", report_id}`. Свои штрихи и уже скрытые — `invalid`. Лимит: 10 жалоб в час на сессию; повтор того же `request_id` идемпотентен.
- Блок авторов фильтрует **клиент** по `author`: серверу не нужен список блоков и лишние условия в snapshot-запросе.

### Хранение

| Таблица | Содержимое |
| --- | --- |
| `stroke_reports` | report UUID, reporter digest, reason, created_at, status open/actioned/dismissed, actor/decided_at |
| `stroke_report_items` | report UUID, stroke UUID |
| `strokes.moderation` | `visible` / `held` (скрыт порогом жалоб до решения) / `hidden` (существующее админ-скрытие) |
| `banned_owners` | owner digest, причина, operation UUID, created_at |

- **Порог:** при 5 жалобах от разных reporter digest штрих переходит в `held`: публичный `stroke.deleted`, snapshot его не отдаёт. Модератор подтверждает (→ `hidden`) или отклоняет (→ `visible`, обычный `stroke.created` со старым seq). Злоупотребление порогом ограничено rate limit и решением модератора.
- **Бан автора:** атомарно скрывает все его видимые штрихи (с аудитом, как hide) и отвечает его сессии `banned` на `stroke.create`. Новый анонимный секрет бан обходит — честное ограничение анонимного холста; повторные нарушения ловятся жалобами/порогом.
- **Уведомление:** новая жалоба или срабатывание порога → сообщение Telegram-бота в чат владельца: причина, число штрихов, сколько открытых жалоб, ссылка на `/admin/`. Без геометрии, digest и UUID жалобщика. Токен бота и chat id — секреты runtime env на VPS, не в репозитории. Отправка асинхронная с повтором; недоступность Telegram не влияет на приём жалоб (очередь в админке — источник истины).

### Admin API

`GET /api/admin/reports?status=open` (список с stroke ids, reason, count, первая/последняя жалоба), `POST /api/admin/reports/{id}/dismiss`, существующий hide для подтверждения, `POST /api/admin/bans` (по stroke id, сервер сам находит owner digest). Те же MFA/CSRF/аудит, что у hide.

## 5. Админка: почему тормозит и что переделать

Найдено в `src/admin/view.ts` / `world.ts`:

1. **Переподписка на каждый pointermove.** `applyCamera` зовёт `setBounds(subscriptionBounds(...))` без `needsResubscribe`: при pan каждые ~260 мс уходит новый полный snapshot, сцена уходит в `loading`.
2. **Полная перерисовка всех штрихов Canvas 2D на каждый кадр**, с сортировкой по seq каждый раз; ни тайлов, ни отсечения по экрану.
3. **Выделение сбрасывается при любом сдвиге камеры** (`applyCamera` → `selected.clear()`): нельзя выбрать штрихи, сдвинуть вид и выбрать ещё.
4. `bounds()` через `Math.min(...spread)` на каждый выделенный штрих в каждом кадре и на каждый клик по всем штрихам.
5. Snapshot end заменяет всю сцену — та же проблема исчезновения при pan, что была на публичном холсте.

Переделка:

- Рендер — общий `createSceneRenderer` (WebGL2 + тайлы, fallback Canvas 2D), как на публичном холсте; выделение и подсветка жалоб — отдельный прозрачный 2D-слой поверх.
- Подписка — `needsResubscribe` + prefetch по направлению, как в `main.ts`; сцена с сохранением штрихов за краем области (тот же механизм, что `SharedScene`).
- Выделение переживает pan/zoom; хит-тест по `strokeExtent` из кеша.
- Новая панель **Reports**: очередь открытых жалоб, клик → камера на штрих и его подсветка, действия Hide / Dismiss / Ban author. Счётчик открытых жалоб в заголовке.
- Бан без жалобы (20.11.2026): у выделения на холсте рядом с «Проверить скрытие» есть **«Забанить авторов…»** — тот же `POST /api/admin/bans` с выбранными id (1–100): авторы всех выбранных штрихов банятся, все их видимые штрихи скрываются, их жалобы закрываются. Подтверждение с обязательной причиной, как у скрытия.
- Тот же минималистичный стиль, что палитра (`docs/design/context-palette.svg`).

## 6. Автодеплой и правило «не пушить в main»

Сейчас: backend `deploy.yml` («Deploy staging», фактически выкладывает endlessdrawing.com) запускается только вручную с `frontend_ref`; у frontend нет CI вовсе; ветки main не защищены; environment без правил.

Предлагаемый поток:

```
feature-ветка ─► PR ─► CI зелёный ─► merge в main ─► автоматический deploy production
```

- **frontend:** новый `.github/workflows/ci.yml` (check, unit, build, e2e Chromium) на PR и push. На push в main — job `trigger-deploy`: `repository_dispatch` (`frontend-main`, sha) в backend. Нужен fine-grained token `BACKEND_DISPATCH_TOKEN` (только backend repo, Contents: read & write) в секретах frontend.
- **backend `deploy.yml`:** триггеры `push: main`, `repository_dispatch: [frontend-main]`, `workflow_dispatch` (ручной откат/повтор). `frontend_ref` = sha из dispatch, иначе текущий frontend main. Переименовать в «Deploy production», environment `production` с политикой «только main». `concurrency: endlessdrawing-production`, без отмены идущего: из очереди GitHub выполняет последний.
- После deploy — автоматически `public-smoke` (readyz, admin закрыт без сессии, WS hello v4/v5).
- **Защита main** в frontend и backend: PR обязателен (без обязательного approve — владелец один), обязательные проверки CI, запрет force-push, действует и для администраторов (иначе правило не остановит ни человека, ни агента). iOS-репозиторий остаётся как есть: деплоя нет, публикацией владелец управляет сам.
- Правило для агентов — в `AGENTS.md` обоих репозиториев: работать в ветке, открывать PR, не пушить в main и не мержить без явного «да» владельца.

## 7. Порядок работ

1. CI/CD и защита main — чтобы всё дальнейшее шло через PR.
2. Backend: v5 (`author`, `stroke.report`), таблицы, порог, бан, Admin API, уведомления.
3. Админка: производительность + очередь жалоб.
4. Web: `/terms`.
5. iOS: согласие, меню `…`, режим жалобы, скрытое, контакты; повторная отправка и ответ в Resolution Center.

Web-жалобы на публичном холсте — после iOS тем же протоколом (Apple их не требует, но холст общий).
